# AIエージェント実験場

メインエージェント、サブエージェント、関連リソースをどう組み替えたら
全体としてどういう挙動になるかを頻繁に組み替えながら実験するためのリポジトリ。

ユースケース単位で単一のエージェントを提供するサービスはたくさんあるが、
内側のサブエージェントを細かく操作できるものがなかなかないので独自に構築している。

## 開発・デバッグ

### 準備

- Node.js 22 以上が必要（nvm-windows なら `nvm use 24.21.0`）。
- `npm install`
- `apps/server/.env.example` を `apps/server/.env` にコピーし、`OPENROUTER_API_KEY` を設定する。
  エージェントのプロバイダに Gemini を選ぶなら `GOOGLE_GENERATIVE_AI_API_KEY`（Google AI Studio の API キー）、
  Web検索ノードを使うなら `TAVILY_API_KEY`、判定ノード（Jev）を使うなら `TYPESAFE_API_KEY` も設定する。

### 起動

- `npm run dev` でサーバー（http://localhost:8787）と画面（http://localhost:5173）が同時に起動する。
  画面からの `/api` はサーバーへ転送される。
- ブレークポイントを使うときは、VS Code で `ai-agent-playground.code-workspace` を開き、
  「実行とデバッグ」から「デバッグ」を起動する。JavaScript Debug Terminal で `npm run dev` が動くので、
  `apps/server/src` の TypeScript にそのままブレークポイントを置ける。
  画面側はブラウザの開発者ツールでデバッグする。

### 構成の考え方

- グラフは会話（セッション）ごとに1つ持ち、ターンは実行時のグラフの写しを残す。新規の会話は今のグラフを写して始まる。
- ノードは ユーザー入力・ユーザー出力・エージェント・フォルダ・判定（Jev）・Web検索 の6種類、エッジは2種類。
  - ツール（上下の接続口）：エージェントが相手をツールとして使う。フォルダへのツールには参照・編集の権限がある。
  - フロー（左右の接続口）：出力を次のノードの入力として流す。判定ノードから出るフローには、回答による条件を付けられる。
- ターンは、ユーザーの発言をユーザー入力ノードから流し、流れの順にノードを1回ずつ実行し、ユーザー出力ノードへ流れ込んだものを返答にする。
  入力と出力を別のノードにしているので、フローを左から右へ一方向に並べられる。
  既定の構成は ユーザー入力 → エージェント（前回までの経緯: このエージェントへの依頼と応答（このセッション））→ ユーザー出力。
- エージェントに渡すもの・返すものはノードで決まり、ツールから呼ばれてもフローから呼ばれても同じ。
  - LLM には、システムプロンプト・前回までの経緯・今回のメッセージの順に渡す。
  - 前回までの経緯は、次のうち1つだけを選ぶ（同じ発言が二重に入らないように）。
    - ユーザーとの会話（前のターンまでの直近 N 発言・すべて）
    - このエージェントへの依頼と応答（ツールコールを含む。このターン・このセッション）
  - 今回のメッセージは、添付ファイル（ワークフォルダのファイルのその時点の中身）と依頼を並べたもの。
    依頼は、フローから呼ばれたときは流れてきた入力、ツールとして呼ばれたときは呼び出し元が書いた引数。
  - 返すものは 最終テキスト・全ステップ・なし。なしのエージェントは終了用のツール finish を持ち、応答の文章を待たずに終われる。
    フローでは受け取った入力をそのまま先へ流すので、ユーザー入力 → なしのエージェント → エージェント と直列に前処理を挟める。
    同じ出所の出力が複数の経路から届いたときは1つにまとめる。
- ワークフォルダはセッションに1つ。フォルダノードはその中のフォルダ（空のパスなら全体）を表し、
  エージェントからのツールエッジでそのフォルダ以下への権限を与える。エージェントはどのフォルダへの権限でも、1組の workfolder_* ツールで操作する。

### 挙動の確認

- チャット欄
  - ノードの呼び出しが実行順に並び、エージェントの中では LLM へのリクエスト（ステップ）とツールコールが時系列に並ぶ。
  - ステップの行にはトークン数・所要時間（ツールの実行は含まない）・コストが出て、開くと
    LLM への生のリクエスト（システムプロンプト・履歴・ツール定義）とレスポンスを見られる。
  - ツールコールを開くと入出力が見られる。ノードの呼び出しならその中身が入れ子で見られる。
  - 欄の上部には、表示中の分岐全体の集計が出る。
- サーバーのコンソールには HTTP のアクセスログと、LLM 呼び出しのエラーが出る。
- ターンのイベントは `GET /api/turns/<turnId>/events`（SSE）で、保存済みのものから再生して取得できる。
- ワークフォルダのファイルは画面右のワークフォルダ欄で、表示中のターン時点の中身を見られる。親ターンから追加・変更されたファイルには印が付く。
  API では `GET /api/turns/<turnId>/files` で、ワークフォルダの中身と、親ターンから変わったパスを取得できる。

### データ

- セッション（グラフを含む）・ターン・ログ・ファイルはすべて `apps/server/data/playground.db`（SQLite）に保存される。
  場所は `.env` の `DATABASE_PATH` で変えられる。
- 各ターンは、終わった時点のファイルと、エージェントへの依頼と応答の写しを持ち、次のターンは親ターンの写しから始まる。
  そのため過去のターンからやり直すと、その時点の状態に戻る。
- まっさらな状態に戻すには、サーバーを止めて `apps/server/data` を削除する。
- 実行中にサーバーを止めたターンは、次の起動時にエラー終了として閉じられる。
- テーブル定義を変えたら `npm run db:generate -w server` でマイグレーションを生成する。
  マイグレーションはサーバー起動時に自動で適用される。

### API キーなしで試す

`.env` の `OPENROUTER_BASE_URL` に OpenAI 互換の Chat Completions API（ストリーミング対応）を返すサーバーを指定すると、
プロバイダが OpenRouter のエージェントは、OpenRouter の代わりにそちらへリクエストを送る。

### テスト・型チェック

- `npm test`：実行エンジンのテスト。LLM はモックで、データベースは一時ファイルを使うので、API キーも既存データも不要。
- `npm run typecheck`：全パッケージの型チェック。
